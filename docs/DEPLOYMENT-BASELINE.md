## How code reaches this box

```
GitHub  origin/production
   │
   │  systemd timer, every 60s
   ▼
frankenstein-deploy.timer → frankenstein-deploy.service → scripts/autopull.sh
   │
   │  DESIRED = origin/production      (git fetch; a failed fetch deploys NOTHING)
   │  RUNNING = ~/.frankenstein/deployed.json .running_commit
   │  deploy only when they differ
   ▼
scripts/deploy.sh
   │  git fetch → checkout → reset --hard origin/production
   │  bash scripts/test.sh          ← THE GATE. Fails ⇒ containers untouched.
   │  docker compose up -d --build --remove-orphans
   │  docker image prune -f
   ▼
records success + running_commit in ~/.frankenstein/deployed.json
```

**Local git HEAD is never consulted.** `deploy.sh` resets to production
*before* the test gate, so a commit whose tests fail leaves HEAD at production
while the containers still run the previous build. An earlier HEAD-based check
read that state as converged and permanently suppressed the retry — it wedged
this box live during the protocol bootstrap. The comparison is deliberately
against the recorded *last successful deploy* instead.

A missing, unparseable, or null record means **unknown**, which is treated as
"deploy required". A running commit is never inferred or manufactured.

### The systemd unit as installed

```ini
# /etc/systemd/system/frankenstein-deploy.service
[Service]
Type=oneshot
User=antdag3
Environment=FRANKENSTEIN_DIR=/home/antdag3/FrankensteinCentral
Environment=FRANKENSTEIN_BRANCH=claude/personal-app-hub-vvpy4h   ← overridden below
ExecStart=/usr/bin/env bash /home/antdag3/FrankensteinCentral/scripts/autopull.sh

# /etc/systemd/system/frankenstein-deploy.service.d/branch.conf   ← drop-in
[Service]
Environment=FRANKENSTEIN_BRANCH=production
```

The drop-in wins — systemd applies drop-ins after the main unit — so the
effective branch is **`production`**. Verified against the live journal, which
shows the poller running each minute and taking no action.

> The stale `claude/personal-app-hub-vvpy4h` line in the base unit is
> harmless today but is a trap: anyone who deletes or edits the drop-in without
> reading the base unit will silently repoint production at a task branch.
> Correcting the base unit would make the configuration self-evident.

Timer: `OnBootSec=30s`, `OnUnitActiveSec=60s` — active and firing on schedule.

## Observations

Findings from this baseline, most consequential first. None is an outage; all
are recorded so they are decisions rather than surprises.

### 1. `.github/workflows/deploy.yml` still bypasses the production boundary

The workflow triggers a deploy on every push to
`claude/personal-app-hub-vvpy4h` **and** `main`:

```yaml
on:
  push:
    branches:
      - claude/personal-app-hub-vvpy4h
      - main
```

That is exactly the behavior the production-branch boundary was built to
eliminate — a review push becoming a deploy. `scripts/autopull.sh` was fixed;
the GitHub Actions path was not.

**It is inert right now.** The job requires a `[self-hosted, frankenstein]`
runner, and no runner is installed on this box: there is no `~/actions-runner`
directory and no `actions.runner.*` systemd unit. Nothing can pick the job up.

**The risk is that it is dormant, not absent.** Anyone following
`docs/SETUP-DEPLOY.md` Option A installs a runner, and the boundary is
reopened silently — pushes to a task branch would deploy again. Restricting the
workflow to `production`, or deleting it in favour of the poller, would close
this permanently.

### 2. `docs/SETUP-DEPLOY.md` still instructs a task-branch checkout

The "One-time prep" section says `git checkout claude/personal-app-hub-vvpy4h`.
Following it verbatim leaves a fresh box pointed at a task branch. The same
document later explains the production boundary correctly, so it contradicts
itself; the setup steps predate the boundary.

### 3. Configuration drift {#configuration-drift}

**Set in `.env` but read by nothing** — dead configuration:

`JELLYFIN_API_KEY`, `JELLYFIN_URL`, `JELLYFIN_USER_ID`, `JELLYFIN_WEB_URL`,
`POWERBUY_WEB_URL`, `VAULT_WEB_URL`

The Jellyfin variables are the residue of a jellyfin sub-app that no longer
exists in `docker-compose.yml`, `services/`, or the gateway registry — only its
stale image remains. `POWERBUY_WEB_URL` and `VAULT_WEB_URL` are in neither
compose nor `.env.example`.

**Read by compose but unset in `.env`** — running on defaults:

| Variable | Effective value | Consequence |
|---|---|---|
| `PLEX_TOKEN`, `PLEX_SERVER_NAME`, `PLEX_URL` | empty | The Plex sub-app runs **"not connected"**. It is `up` because it is healthy, not because it has data. |
| `LOCAL_TZ` | `America/New_York` | Correct here, but by default rather than by decision — and this is the variable the 2026-09-01 date bug turned on. |
| `GOOGLE_CALENDAR_ID` | `primary` | Fine. |
| `GMAIL_REFRESH_SECONDS` | `21600` (6h) | Fine. |
| `GMAIL_QUERY` | empty | Primary tab, last 7 days. |
| `GOOGLE_REFRESH_TOKEN` | empty | Consent flow is used instead; the token on the volume is what matters. |
| `FIREFLY_IMPORTER_URL` | empty | The importer deep link has no target. |
| `TWILIO_*`, `NOTIFY_TO`, `NOTIFY_WEBHOOK_URL` | empty | `NOTIFY_CHANNEL` is set to a Telegram-based channel, so these are not needed. |

`.env` and `.env.example` have also drifted apart: `.env` carries four
`JELLYFIN_*` keys plus two `*_WEB_URL` keys the template lacks, while the
template carries `FIREFLY_IMPORTER_URL`, `LOCAL_TZ` and the three `PLEX_*` keys
that `.env` lacks. A fresh box built from the template would not match this one.

### 4. ~2.6 GB of orphaned images

Fifteen images remain from the old **underscore** compose project name
(`frankensteincentral_gateway`, `_assistant`, … ), plus
`frankensteincentral-jellyfin` and `frankensteincentral_jellyfin` from the
removed sub-app. Docker renamed the project separator from `_` to `-`, and
`docker image prune -f` does not remove them because they are tagged, not
dangling.

At 168–182 MB each this is roughly 2.6 GB. Disk is at 45%, so this is
housekeeping, not pressure.

### 5. `activity` grows without bound

The assistant's `activity` table holds ~33,500 rows spanning 2026-07-21 to
2026-09-05 — about 730 rows/day, 4.4 MB, and the largest object in a 13 MB
database. Reads are capped at 30 rows; writes are never pruned. Nothing depends
on the old rows. At the current rate it adds ~35 MB/year, so a retention policy
is worth having eventually, not urgently.

### 6. Legacy `budget` table

The `budget` table still exists and is empty. The budget service became
stateless — definitions moved to `core_settings`, transactions come from the
firefly service — and nothing reads or writes it. Dropping it would be a
destructive migration and therefore requires approval; leaving it costs
nothing.

## Verifying this baseline yourself

```bash
cd ~/FrankensteinCentral

bash scripts/frankenstein-status.sh          # turn, status, desired vs running
cat ~/.frankenstein/deployed.json            # the raw deployment record
systemctl cat frankenstein-deploy.service    # unit + drop-ins, in apply order
systemctl list-timers frankenstein-deploy.timer
journalctl -u frankenstein-deploy.service --since '-1 h'

docker compose ps                            # containers in this project
curl -s localhost:8080/api/health | python3 -m json.tool   # all 15 sub-apps
```

To confirm the boundary itself still holds, push a harmless throwaway branch
and check that nothing deploys — never use a product change for this:

```bash
git push origin HEAD:refs/heads/throwaway-boundary-test
sleep 90
journalctl -u frankenstein-deploy.service --since '-2 min' | grep -i deploy   # expect nothing
git push origin --delete throwaway-boundary-test
```

## Maintaining this file

Re-take the baseline when the deployed commit changes, when a service is added
or removed, when the systemd unit or its drop-ins change, or when `.env` is
edited. Record what was **observed**, never what is expected — the value of
this document is entirely in it being a measurement.
